# Дорожная карта: подключение фронтенда к FastAPI

> **Исходный план.** Часть этапов уже выполнена, а часть решений изменилась (например, `progress_log` вместо `watch_log`, заметка `comment` вместо `reviews`). Актуальный статус и обновлённые промпты: [roadmap_frontend_v2.md](roadmap_frontend_v2.md). Работайте по нему.

Порядок такой, чтобы приложение работало после каждого этапа, а не только в конце. Каждый промпт можно вставлять в Claude Code из корня проекта. Правила из `CLAUDE.md` он подхватит сам.

## Этап 0. Аудит и контракт

**Цель:** понять, чем модель фронтенда отличается от бэкенда, до написания кода.

**Результат:** файл `docs/api-contract.md` с таблицей соответствий и списком расхождений.

```text
Прочитай frontend/src/lib/store.ts, rules.ts и типы тайтла во фронтенде, а также backend/schemas.py и scripts/schema.sql.
Ничего не меняй в коде. Составь docs/api-contract.md:
1. Таблица полей: поле фронтенда ↔ поле бэкенда (имя, тип, nullable).
2. Таблица значений: категории (series/anime/… ↔ tv_series/anime/…) и статусы (done ↔ completed и т.д.).
3. Список того, что есть на фронтенде, но нет в БД (описание, отзывы, журнал просмотров, «всего серий», и т.п.).
4. Список эндпоинтов, которых не хватает экранам (статистика, лента, поиск по каталогу).
5. Предложение, что добавлять в бэкенд, а что оставить во фронтенде.
В конце задай мне уточняющие вопросы по спорным местам.
```

## Этап 1. Расширение бэкенда под фронтенд

**Цель:** в БД появляется всё, что нужно экранам.

**Результат:** новые поля и таблицы, тесты зелёные, существующие данные не потеряны.

Важный момент: `init_db --reset` стирает данные, а Alembic по правилам проекта нельзя. Поэтому изменения в `schema.sql` нужно писать идемпотентно (`ADD COLUMN IF NOT EXISTS`, `CREATE TABLE IF NOT EXISTS`).

```text
По docs/api-contract.md расширь бэкенд. Правила: schema.sql + models.py + schemas.py одновременно, Alembic не добавлять.
1. В media_items: description TEXT, total_episodes INTEGER (CHECK >= 1), total_chapters/total_volumes, если нужны фронтенду.
2. Новая таблица watch_log (id, item_id FK ON DELETE CASCADE, season, episode, chapter, logged_at) для ленты и статистики.
3. Новая таблица reviews (id, item_id FK CASCADE, text, rating, created_at), если фронтенд хранит отзывы отдельно.
4. Изменения в schema.sql пиши так, чтобы init_db без --reset применял их к уже существующей базе и не терял данные (ADD COLUMN IF NOT EXISTS и т.п.).
5. Эндпоинты: POST /items/{id}/log (отметить серию/главу, одновременно обновляет прогресс), GET /items/{id}/log, CRUD для reviews.
6. Пагинация в GET /items/ (limit, offset) без поломки существующего контракта.
Напиши тесты, запусти pytest, покажи результат.
```

## Этап 2. Безопасный мост Next.js → FastAPI

**Цель:** браузер ходит только в Next.js, а FastAPI закрыт от внешнего мира.

**Результат:** все запросы к API идут через авторизованную сессию.

Сейчас вход сделан на стороне Next.js, а в FastAPI авторизации нет. Если открыть FastAPI наружу, любой сможет читать и стирать данные. Решение: Next проксирует `/api/backend/*` во FastAPI (сессию уже проверяет `proxy.ts`), а FastAPI слушает только `127.0.0.1`.

```text
Сделай прокси фронтенда к FastAPI.
1. В .env.example добавь BACKEND_URL (по умолчанию http://127.0.0.1:8000). Значение в .env не трогай.
2. Реализуй проксирование /api/backend/* → BACKEND_URL/* (rewrites в next.config.ts или route handler). Убедись, что запросы без сессии получают редирект/401 через src/proxy.ts.
3. Поддержи multipart (загрузка постера) и отдачу /posters/*.
4. Запуск FastAPI в документации поменяй на --host 127.0.0.1 и убери лишний CORS, если он больше не нужен.
5. Добавь vitest-тест на защиту маршрута и обнови frontend/README.md.
```

## Этап 3. Слой-адаптер `src/lib/api.ts`

**Цель:** вся «грязь» преобразования форматов в одном месте.

**Результат:** компоненты ничего не знают про `tv_series` или `completed`.

```text
Создай frontend/src/lib/api.ts (адаптер к бэкенду через /api/backend):
- типы ответа бэкенда (ApiItem) отдельно от типов интерфейса;
- функции toUiItem / toApiPayload / toApiPatch: маппинг категорий, статусов, null ↔ undefined, массива genres, poster_url (/posters/... → полный путь через прокси);
- функции: listItems, getItem, createItem, patchItem, deleteItem, logProgress, uploadPoster, deletePoster, а также работа с reviews и логом;
- единый тип ошибок: ApiError с кодом и русским текстом (404, 422, 502, 503);
- повторы не нужны, таймаут запроса есть.
Без новых npm-пакетов, на fetch. Компоненты не трогай.
Напиши vitest-тесты на все мапперы (в том числе краевые: пустые поля, неизвестная категория, строка 422 с деталями Pydantic).
```

## Этап 4. Переключение стора на API

**Цель:** localStorage перестаёт быть источником данных.

**Результат:** данные живут в PostgreSQL, интерфейс остаётся быстрым.

```text
Переведи frontend/src/lib/store.ts с localStorage на API через src/lib/api.ts. Компоненты по возможности не менять.
- Состояния loading / error / ready для библиотеки, скелетоны используем текущие.
- Оптимистичные обновления для «+1 серия», рейтинга и статуса с откатом и toast при ошибке.
- Zustand persist оставь только для темы и языка; библиотека из localStorage больше не читается.
- Демо-данные только за флагом (например, NEXT_PUBLIC_DEMO=1), по умолчанию отключены.
- Первая загрузка: GET /items/ с пагинацией до конца.
Тесты vitest на логику стора (с замоканным api). Затем запусти typecheck, test и build.
```

## Этап 6. Постеры и обогащение в интерфейсе

**Цель:** работает загрузка своих постеров и ручной выбор варианта.

```text
Подключи в интерфейсе возможности постеров и обогащения:
1. Кнопка «Загрузить свою картинку» (JPEG/PNG/WebP, до 5 МБ) → POST /items/{id}/poster; клиентское уменьшение до 480 px убери, если оно мешает серверу.
2. «Удалить постер» → DELETE.
3. В карточке кнопка «Найти данные» → GET enrich/candidates → модалка с вариантами (постер, название, год, источник) → POST enrich/apply. Отдельный чекбокс «Заменить постер» (force=true).
4. Ошибки 502/503/404/400 показывай понятными сообщениями из README бэкенда.
5. Экран/раздел «Требуют проверки», который читает записи без постера или с пустыми полями (чтобы заменить ручную работу с data/enrich_review.json).
Тесты логики и обработки ошибок.
```

## Этап 7. Статистика и лента с сервера

**Цель:** аналитика считается по реальному журналу, а не по демо.

```text
Добавь серверные эндпоинты (с тестами на PostgreSQL):
- GET /stats: распределение по жанрам и странам (по массиву genres), по годам релиза, по статусам и категориям, топ тайтлов по числу отмеченных серий из watch_log, активность по дням за период.
- GET /feed: события из watch_log и reviews с курсорной пагинацией для бесконечного скролла.
Затем подключи экраны «Статистика» и «Лента» к ним через api.ts. Анимацию статистики сохрани. Расчёты на фронтенде оставь только для отображения.
```

## Этап 8. Каталог «Обзор» на внешних источниках

**Цель:** статический каталог заменяется живым поиском.

```text
Сделай каталог живым:
1. Бэкенд: GET /catalog/search?q=&category= использует существующие провайдеры из backend/enrich/ (тот же Provider, лимиты и User-Agent), ничего не сохраняет, возвращает кандидатов.
2. Если нужны новые источники (например, AniList), добавь отдельный класс-провайдер и зарегистрируй в PROVIDER_CLASSES; без новых зависимостей.
3. Фронтенд: поиск в «Обзоре» с debounce, кнопка «Добавить в библиотеку» создаёт запись и применяет выбранного кандидата.
4. Команда «Добавить тайтл» в палитре Ctrl+K ищет через этот же эндпоинт.
Внешние API в тестах только через MockTransport и fixtures.
```

## Этап 9. «Эпи»: ИИ-компаньон

**Цель:** вместо правил ответы с учётом твоей библиотеки.

Это потребует новую зависимость (SDK) и ключ в `.env`, поэтому разрешение нужно дать явно.

```text
Разрешаю добавить официальный SDK Anthropic в requirements.txt (только в .venv).
Реализуй POST /ai/chat:
- ключ из .env (ANTHROPIC_API_KEY, .env не читай, добавь только в .env.example), если ключа нет → 503 с понятным текстом;
- контекст: сжатая выжимка библиотеки (жанры, топ оценок, что в процессе), а не вся база;
- стриминг ответа, лимит длины запроса и частоты, ошибки как 502/503;
- функции: рекомендации «что смотреть дальше», структурирование рецензии из пары слов (черновик, который пользователь подтверждает кнопкой, никогда не сохраняется автоматически).
Фронтенд: экран AI-чата подключи к эндпоинту, текущие правила из epi.ts оставь как запасной вариант при ошибке. Тесты с моком клиента, реальных вызовов в тестах нет.
```

## Что стоит помнить

- **Коммит после каждого этапа**, и не переходи дальше, пока зелёные `pytest`, `typecheck`, `test` и `build`.
- **Этапы 1–5 обязательны**, они дают рабочее приложение на реальной базе. Остальные можно переставлять по интересу, но 6 (постеры и обогащение) полезнее всего сделать сразу, пока в базе много записей без обложек.
- **Новые зависимости** (этапы 9 и 11) разрешай только явно, как в промптах выше. Это соответствует правилу в `CLAUDE.md`.
- **Если этап слишком большой**, пиши Claude Code: «разбей на подзадачи и сделай только первую».
